Этот документ фиксирует правила работы над визуальными экранами Witcher LARP,
чтобы новый чат быстро продолжал UI/UX работу без отката к “сайтовым”
прямоугольникам поверх красивого арта.

## Базовый принцип

Делаем не лендинг и не админскую страницу, а игровые экраны. UI должен
ощущаться частью сцены: металлические пазы, карты, панели, таблички, слоты и
интерактивные зоны должны совпадать с нарисованными ассетами, а не лежать
поверх них чужими CSS-блоками.

Работа идет по одному экрану за раз. Не смешивать вход, карту, замок, сражение,
карточный стол и мобильные роли в одном макете или одном обсуждении.

## Обязательный порядок работы над экраном

1. Уточнить роль, устройство и сценарий экрана.
   Для лордов базовая поверхность - компьютерный браузер, не телефон.

2. Зафиксировать reference grammar.
   Пример: для входа лордов - Warcraft 3 main menu: фон, логотип слева,
   тяжелая подвешенная табличка справа, объемные кнопки внутри пазов.

3. Сформулировать состав экрана до генерации.
   Нужно перечислить только то, что видит игрок. Не добавлять служебные
   подписи, API-комментарии, debug labels, acceptance notes или объяснения
   прямо на игровой экран.

4. Сначала собрать/сгенерировать визуальные ассеты.
   Для игровых экранов предпочтительны bitmap-ассеты и слоеная композиция:
   фон, табличка, карты, вырезки локаций, hover masks, UI slots.

5. Потом посадить активный UI поверх ассетов.
   Hit-zone, текст, input, hover и drag/drop должны попадать в уже нарисованные
   игровые формы. Если слот нарисован на PNG, активная зона привязывается
   абсолютными процентными координатами к этому слоту.

6. Добавить motion design только после статического совпадения.
   Сначала добиться правильной посадки и визуальной целостности, затем
   анимировать входы, hover, переходы и idle-состояния.

7. Проверить экран скриншотами.
   Минимум: обычное состояние, hover/active состояние, целевое состояние после
   перехода. Для точной проверки делать крупный crop проблемной панели.

## Инструменты

### React + Tailwind

Использовать для интерактивного UI, layout, state, role flows и integration с
API. Tailwind подходит для геометрии, адаптива и базовых эффектов, но не должен
создавать чужие прямоугольники поверх игрового арта.

### Motion for React

Использовать для настоящей интерактивной анимации:

- переходы между состояниями экрана;
- уход/возврат панелей;
- появление содержимого через `AnimatePresence`;
- тяжелые spring-анимации;
- idle-анимации фона, света, логотипа.

Для прототипа Stage 2B dependency подключена в
`prototypes/stage2b-v2/package.json` как `motion`.

### OpenRouter

Основной инструмент генерации изображений, если нужны новые bitmap-ассеты.
Причина: дешевле для итераций, чем Recraft/Ideogram. Использовать подробные
промпты с указанием композиции, материала, освещения, UI-safe empty slots,
front-facing object, transparent/chroma background when needed.

Текущие ключи пользователь хранит вне этого repo:
`C:\ianssens\projects\AI_OS-1\.env`. Не выводить ключи в чат и не коммитить.

### Ideogram

Использовать точечно для логотипов и типографических ассетов, когда важна
красивая надпись. Это дороже, поэтому не использовать для каждой мелкой
итерации. Если логотип уже принят, не регенерировать его без явного запроса.

### Recraft

Использовать точечно для UI-плашек, иконок, векторно-похожих элементов или
style-consistent asset variants. Это дороже, поэтому сначала пробовать
OpenRouter, если качество достаточно.

### Figma MCP

Использовать для:

- фиксации визуальных экранов;
- handoff в дизайн;
- сравнения вариантов;
- сборки acceptance boards;
- передачи структуры экранов между чатами.

Не использовать Figma как основной runtime для игровой анимации. Интерактивное
поведение должно жить в React.

### Higgsfield MCP

Если подключен, использовать как motion-reference/video-reference tool:
сгенерировать короткий клип “как должна двигаться панель/цепи/камера”.
Не считать Higgsfield заменой интерактивной React-анимации. Видео-референс
помогает вкусу, но кликабельный экран реализуется в коде.

### Browser / Chrome screenshots

После значимых frontend-правок обязательно проверять локальный экран в браузере
или headless Chrome. Пользователь оценивает картинку, поэтому “сборка прошла”
недостаточно.

Если `vite build`/Vite prototype build на Windows падает внутри Codex sandbox
с `Error: spawn EPERM` из `esbuild` при загрузке `vite.config.ts`, считать это
ограничением sandbox на запуск дочернего процесса, а не ошибкой приложения или
Vite-конфига. Нужно повторить ровно ту же команду с
`sandbox_permissions: "require_escalated"` и коротким justification, затем в
отчете указать оба факта: sandbox failure и результат escalated build.

## Правила ассетов

- Не копировать официальный Witcher, Warcraft, Heroes или Gwent art.
  Референсы задают структуру и настроение, production/prototype assets должны
  быть original/local/generated.
- Для “сам объект выделяется” делать отдельный слой: cutout PNG/WebP с
  прозрачностью, маска или hotspot, а не просто круг/прямоугольник поверх
  красивого фона.
- Если объект должен увеличиваться при hover, лучше иметь отдельную вырезку
  объекта и анимировать ее поверх базового фона.
- Если UI должен быть “внутри картинки”, сначала генерировать/рисовать
  физический слот, затем привязывать интерактивный слой к этому слоту.
- Для игровых кнопок предпочтительны нарисованные пазы/таблички и активные
  hit-zone поверх них, а не обычные CSS-кнопки.
- Проверять текст на русском: на игровых экранах не оставлять английские слова,
  placeholder, debug labels или технические подписи.

## Правила motion design

- Motion должен объяснять физику сцены: тяжелая панель тянет цепи, кнопка
  вдавливается, свет вспыхивает в пазу, карта поднимается из руки.
- Не анимировать все одновременно. Главный объект перехода один.
- Для перехода “Вход” текущая approved grammar:
  1. кнопка `Вход` вдавливается;
  2. правая табличка чуть проседает;
  3. табличка уходит вверх за экран;
  4. содержимое меняется вне экрана;
  5. табличка возвращается с тяжелым spring;
  6. появляются `Код лорда`, `Введите код`, `Войти`, `Назад`.
- Поддерживать `prefers-reduced-motion`.
- Для отладки можно использовать query params, но они не должны быть видимыми
  элементами UI. Пример: `?view=login`, `?hover=enter`, `?motion=slow`.

## Правила работы с одним экраном

Перед началом следующего экрана в новом чате:

1. Прочитать этот документ.
2. Открыть текущий прототип:
   `prototypes/stage2b-v2`.
3. Уточнить у пользователя один экран и один reference set.
4. Сказать, что должно быть на экране, и попросить недостающие референсы.
5. Не переходить к следующему экрану, пока текущий не принят визуально.
6. После принятия сверить экран с API/read-model mapping:
   `docs/ui/stage2b-api-map.md`.

Принятое направление:

- логотип Witcher LARP I слева;
- тяжелая подвешенная табличка справа;
- `Вход` и `Обучение` сидят в нарисованных пазах;
- при hover подсвечивается вся плашка;
- при входе табличка уходит вверх и возвращается с формой:
  `Код лорда`, `Введите код`, `Войти`, `Назад`.

Следующий экран:
`http://127.0.0.1:5178/lords/home`

Канон следующего этапа:

- `/lords/home` после успешного входа показывает основной экран замка или
  выбранной захваченной территории, а не карту;
- композиция должна максимально повторять текущий референс: full-screen фон,
  тонкая верхняя строка ресурсов, круговые иконки действий слева, мини-карта
  снизу слева, две линии армии/гарнизона и найм снизу по центру, плашка акта
  снизу справа и полукруглая шкала MP над ней;
- у территорий тот же UI, но меняются фон, локальный доход, гарнизон, найм и
  минимальное дерево построек;
- если герой-армия не в выбранной локации, верхняя линия армии пустая и
  заблокированная;
- в этом этапе не прорабатывать детально стратегическую карту и поле боя:
  они открываются по иконкам, но проектируются в отдельных чатах.
